# M1: controlled Stripe sandbox workflow

M1 adds payment creation/retrieval, full and partial refunds, and final-state
verification using the installed Stripe 16.1.0 SDK. No dependencies were added.
These operations are explicit local CLI commands. The Flask request-intake API
does not execute payments or refunds, and no LLM is involved yet.

## Commands (Git Bash)

All amounts are integer USD cents. M1 intentionally supports USD only.
The sandbox key is read from the existing ignored `.env`. Keep the same database
and sandbox credentials for retries; changing sandboxes requires a separate
database. Do not delete the operation journal to retry an uncertain write.

```bash
# Fresh read of an existing verified fixture:
.venv/Scripts/python.exe -m payresolve m1 get-payment pi_3UWK4NLAN0BwlmJO1KjDn12M

# Local snapshots and journal (no Stripe requests):
.venv/Scripts/python.exe -m payresolve m1 list-payments
.venv/Scripts/python.exe -m payresolve m1 operation m1-20261030-verified-partial-refund

# Read-only Stripe verification; never submits a new payment or refund:
.venv/Scripts/python.exe -m payresolve m1 verify m1-20261030-verified-partial-refund

# Reuse the existing controlled run. Completed operations are replayed locally:
.venv/Scripts/python.exe -m payresolve m1 fixtures --run-id m1-20261030-verified
```

To deliberately create another test payment and refund part of it:

```bash
.venv/Scripts/python.exe -m payresolve m1 create-payment \
  --operation-id demo-payment-1 --amount 3999

# Replace pi_REPLACE_ME with the returned PaymentIntent ID:
.venv/Scripts/python.exe -m payresolve m1 refund \
  --operation-id demo-refund-1 --payment-id pi_REPLACE_ME --amount 1000
```

Omit `--amount` on `refund` to refund the full remaining amount. Use `--unpaid`
on `create-payment` to create an unconfirmed PaymentIntent. The fixture command
creates a new set when given a new run ID; reuse a run ID to resume/recheck it.
It creates four PaymentIntents and only two refunds, retaining known final states
for subsequent work. A modified fixture causes the final-state check to fail.

Commands print JSON. Exit code 0 means the command completed; payment/refund
commands return `status: verified` only after retrieval checks pass. Exit code 2
means a refund remains pending. Exit code 1 indicates failure or an unresolved
operation. For an unpaid fixture, `verified` means its expected unpaid state was
confirmed; it does not mean money was captured.

## Validation and retry contract

- Only `sk_test_`/`rk_test_` credentials are accepted. Balance, PaymentIntent,
  and Charge objects must confirm `livemode=false`. Refund objects have no
  `livemode` field; verification follows their linked sandbox payment and charge.
- Payment fixtures use synthetic Stripe payment methods, amounts from 50 to
  1,000,000 cents, and no customer/card data.
- Refunds require a locally recorded fixture whose metadata matches its creation
  operation, successful payment status, a paid/captured and undisputed charge,
  matching currency, and a positive integer amount within the remaining balance.
- Before a Stripe POST, SQLite commits the operation ID, immutable input and API
  parameters, preflight snapshot, and a randomly generated Stripe idempotency key.
  A full refund freezes the amount at preparation; a retry cannot silently change it.
- Reuse the **same operation ID and parameters** for the same intended action.
  Changed parameters under the same ID are rejected. Completed results are cached
  across restarts; use `get-payment` or `verify` to refresh Stripe state.
- A new operation ID represents a new intended action. This is retry protection,
  not semantic duplicate detection across separately submitted customer requests.
  Natural-language/request identity linking belongs to M2.
- SQLite write transactions serialize local workflows across processes. A second
  refund on the same payment is blocked while an earlier one is unresolved/pending.
  Lock contention may return `storage_unavailable`; retry with the original ID.
- A lost response is recovered by resending the saved parameters and key, within
  23 hours of preparation. If a Stripe ID is known, retries only retrieve it.
  An unknown ID after that window requires manual reconciliation in Stripe;
  the app refuses to resend, since Stripe may prune idempotency keys after 24 hours.
- `verify` never issues a POST. If the Stripe ID is unknown, rerun the original
  command within the replay window to recover it. Do not invent a new ID after
  an ambiguous failure. Permanent errors also require inspection before proceeding.
- Verification compares refund identity, payment/charge linkage, currency,
  amount, operation metadata, status, and the resulting refunded balance. Pending,
  requires-action, failed and canceled refunds are not labeled successful.
  Historical verification permits additional later refunds while requiring the
  originally verified refund to remain present in the refunded total.
  If later verification contradicts an earlier success, the cached result is
  cleared and the operation becomes unresolved. Its Stripe ID is retained, so
  recovery rechecks the existing object without issuing another POST.

Stripe enforces its own remaining-amount constraint against external concurrent
changes. This local prototype cannot serialize Dashboard activity or another
application. It has no distributed job queue, webhook reconciliation, customer
ownership/authentication layer, or production financial workflow.

## Implementation and tests

- `stripe_gateway.py`: SDK transport, sandbox checks, sanitized errors and minimal snapshots.
- `operations.py`: additive `stripe_operations` and `sandbox_payments` tables; existing
  intake data is preserved.
- `workflow.py`: deterministic validation, durable replay, and final-state checks.
- `m1.py`: explicit CLI commands and repeatable fixtures.

All 42 local tests pass on Python 3.15.1, as does `pip check`. Coverage includes
real SDK request construction with simulated HTTP, schema preservation, CLI exit
codes, concurrency, restarts, lost responses, read failures after writes,
idempotency-window expiry, invalid amounts, unpaid/failed/disputed/uncaptured
payments, pending/failed refunds, and mismatched verification state. Local tests
never read `.env` or call Stripe. The actual sandbox fixture run and fresh-process
replay passed separately.

```bash
.venv/Scripts/python.exe -m unittest discover -s tests -v
.venv/Scripts/python.exe -m pip check
git diff --check
```
